## UI, Android, and offline feasibility

Source inspection: server.py offers GET / and POST /midi-to-midi; templates/index.html uploads the chosen file and downloads a MIDI result. There is no implemented note/group hand-correction interface in that template. No browser or Android device end-to-end test was performed because current server startup fails. A viewport meta tag is not evidence of responsive usability.

The browser depends on a Python server for inference and loads jQuery from a public CDN. Current source does not establish offline Android operation. mobile.py traces a TorchScript artifact with [100,16,4] input, but this is not an Android application or a browser inference integration. Offline runtime, conversion fidelity, memory, storage, packaging, and target-device latency remain unknown. No framework or deployment decision was made.

## Data, labels, and rights

No tracked training MusicXML corpus, split manifest, validated hand-labeled evaluation set, or checkpoint dataset provenance was found. Training expects source_data/musicxml; source_data is ignored. The README describes supervised MusicXML training, but that alone does not validate labels or license the data/checkpoint.

Existing preprocessing splits songs before window generation (shuffle=False), so the earlier generic possibility of window-level split leakage is not a demonstrated defect. Duplicate pieces/arrangements, source ordering bias, held-out representativeness, and label ambiguity still need evaluation. Up to 50 shuffled windows per song are sampled without a fixed seed. Do not claim an accuracy score or superiority over a pitch baseline.

README contains a CC BY-NC 4.0 notice; vendored Magenta parser files contain Apache-2.0 headers. This inventory is not a rights determination. Dataset and sample-music rights, checkpoint provenance, attribution obligations, and intended distribution/use need an explicit review before redistribution or product release. No third-party training data was downloaded or republished.
